## 1章 — `external_user_id` に何を送るか → **確定**

### 回答

| 質問 | 回答 |
|---|---|
| 1-1 `common_user_id` を付与APIが受け付けるか | **受け付けない。追加予定も無い** |
| 1-2 `users.id` を送る案 | **妥当。合っている** |

補足された正式仕様:

- 付与APIのアカウント解決は `service_code` + `external_user_id` のみ。
  `AccountLink` テーブルの `(serviceIntegrationId, externalUserId)` 一意制約で管理される
- `OveAccount.commonUserId` はWallet自身が代理店システムの `POST /api/common-users/resolve` を
  呼んで解決・保存する列。**付与APIとcommon_user_id解決は完全に別経路**
- 既存の全連携先が `service_code` + `external_user_id` 方式で動いているため、この設計を維持する想定
- 「変更が必要になった場合は相談を」との申し出あり

### ★ 新たに判明した重要事項: `external_user_id` は事実上変更できない

- **一度作成した `external_user_id` をリネームするAPI・機能は存在しない。**
  `AccountLink(serviceIntegrationId, externalUserId)` は一意制約のキーで、既存レコードを
  書き換える運用は想定されていない
- 同一人物に複数Walletアカウントができた場合は**アカウント統合機能**で対応する
  - 管理画面「アカウント一覧」→「アカウント統合」
  - **二段階承認制**（申請者と承認者が別の管理者であることが必須。金額によらず常に承認が必要）
  - 承認されると残高・連携（`AccountLink` 含む）が統合先へ移管される
  - **パスポート側から自動で呼べるAPIではない**

→ 「重複アカウントの発生を防ぐには、`users.id` を最初から正しく送ることが重要」との指摘。

### パスポート側の決定

**ADR-6 の [保留] を解除し、確定とする。**

| 用途 | 識別子 |
|---|---|
| パスポート内部（進捗・回答・完了イベント） | `users.id`（uuid） |
| ウォレットへ送る `external_user_id` | **`users.id`** |
| 付与要求に併記して記録 | `common_user_id`（解決済みの場合のみ） |

加えて、変更不能かつ復旧が手動二段階承認である以上、**送信前の検証を実装側で担保する**:

- `external_user_id` は付与要求レコード作成時に確定して保存し、以後**書き換えない**
- 送信直前に「保存済みの値」と「現在の `users.id`」が一致することを確認する
  （取り違えた値を送ると手動統合でしか復旧できないため）
- テスト環境と本番環境で同じ `users.id` が混ざらないよう、`service_integrations` を
  環境ごとに分ける（質問4-2、優先度Bで確認中）

## 2章 — 取引履歴の照会手段 → **§8.4(2) で確定**

### 回答

| 質問 | 回答 |
|---|---|
| 2-1 外部から取引履歴を照会できないという理解 | **合っている** |
| 2-2 取引履歴照会APIの新設 | **予定は未定。計画は無い** |

補足された正式仕様:

- 外部サービス向けに公開されているのは
  `GET /api/v1/service/accounts/{externalUserId}/balance`（HMAC認証、`ExternalApiAuthGuard`）のみ
- `GET /api/v1/me/transactions` は `SessionAuthGuard`（ブラウザセッション認証）専用の
  `api/v1/me` コントローラにあり、**物理的に別コントローラ・別認証ガード**。
  外部サービスのHMAC認証では呼び出せない
- 新設は「一存では決められない設計判断」。必要なら**正式に機能要望として提出**すれば検討する
- 当面は指示書§8.4(2) を推奨。「現状の正本データは非常にシンプル（実質ゼロに近い）なので、
  この方式でも運用負荷は小さいはず」

### パスポート側の決定

**ADR-7 の方針を確定する。** 指示書§8.4(2)（運営が提供する正式な付与済みデータを、
出所・取込日時・更新履歴つきで判定テーブルへ取り込む）を採用する。

取込データが無い間は**付与を保留**する。推測で付与済み判定を作らない。

機能要望として取引履歴照会APIを上げるかどうかは、3章の結果を見てから判断する
（付与実績が実質ゼロなら、当面は不要）。

## 3章 — 旧3,000 OVE の現状 → **「受領済み」という前提は成立していない**

### 回答

| 質問 | 回答 |
|---|---|
| 3-1 全件 `PENDING` か | **合っている** |
| 3-2 別経路での確定付与実績 | **コード上は存在しない**（ただし後述の盲点あり） |
| 3-3 Phase 2・3 の実装時期 | **未定** |

補足された根拠:

- `wallet_referral_benefits` の `status` を書き込むコードは `referral.repository.ts` の**1箇所のみ**で、
  遷移は `CAPTURED → PENDING`（会員登録時）だけ。
  `CONFIRMED` / `REJECTED` / `REVOKED` へ遷移させるコードは**リポジトリ内に一切存在しない**
- 「確定付与は構造的に発生し得ない」
- 「CSV一括付与」「既存ユーザー移行」の機能は、どちらも `wallet_referral_benefits` に一切触れない
- **staging環境の総アカウント数は2件**（初期管理者関連のみ）。実運用データはまだほぼ存在しない段階

### ★ 残る確認事項（コードからは判定できない）

回答者から明示された盲点:

> 管理者が「CSV一括付与」を使って**紹介特典とは無関係に、単発の3,000 OVE付与を
> 個別ユーザーへ直接行った**可能性は、コード上は技術的に可能。
> これは `wallet_referral_benefits` の status には一切反映されず、
> 通常の取引履歴・監査ログにのみ残る。

**確認方法**: ウォレット管理画面の「操作ログ」または「取引一覧」で、
金額3,000・理由に「紹介」等を含む手動付与の有無を確認する。

→ **運営側の作業。** 本書では未確認のままとする。

### パスポート側の決定

**「既存参加者は3,000 OVE を受領済み」という前提は成立していない**と扱う。

これにより、実装指示書の以下が影響を受ける:

| 指示書の箇所 | 影響 |
|---|---|
| §9.2「既存参加者の付与済みOVEを維持する」 | 維持すべき付与が存在しない可能性が高い |
| §9.2「新規向け3,000 OVE相当の重複取得を防止する」 | **防止対象が存在しない可能性が高い** |
| §19.1(4)「旧3,000 OVE一括付与を停止する日時」 | **停止すべき処理そのものが動いていない** |
| §19.1(5)「新制度の対象者判定基準」 | 「3,000 OVE受領済みか」を基準にできない。**定義し直しが必要** |

方針としては指示書§9.2の保留方針を維持する（既存参加者を新規向けコースへ自動登録しない）。
回答者からも「3-1・3-2の回答内容を前提に、§9.2の保留方針のまま進めるのが安全」との推奨があった。

Phase 2・3 の着手が具体化した際はウォレット側から連絡が来る。

### ★ 訂正: `AUTH_MODE=mock` は古い情報だった

回答者からの明示的な訂正:

> 質問書の前提（`docs/deployment.md` 記載の `AUTH_MODE=mock`）は**現在は古い情報**。
> 2026-07-18の実チャネルLINEログイン結合試験の結果を受け、staging環境は
> **`AUTH_MODE=production` に切り替え済み**で、LINEログインは実チャネルで動作している。
> （戦国パスポートSSOはまだモックのまま）
> API（Railway）・管理画面（Vercel）とも現在稼働中。ただし実ユーザー向けの正式公開ではなく、
> 引き続き**検証用の位置づけ**。

**パスポート側の記述を訂正した。** `docs/PASSPORT_LEARNING_MISSION_CURRENT_STATE.md` §12 の
「動作確認用デプロイは `AUTH_MODE=mock`」という記述は、リポジトリ内の
`docs/deployment.md` を読んで書いたものだが、その文書自体が実態より古かった。

**教訓**: 相手方リポジトリのドキュメントも、コードや実環境より古い場合がある。
本件のように「ドキュメントに書いてある」ことを事実として扱う際は、
相手方への確認を経るまで [要確認] の扱いを外さない。
