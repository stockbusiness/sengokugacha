# 国主プラン アイデア記録

> **これは検討メモであり、確定仕様ではない。** 2026-07-29 時点の議論を記録したもので、
> 実装は一切行っていない。着手前に「未確定の論点」を埋める必要がある。

## 発端

城主プランの上位プランとして「国主プラン」を設ける構想。当初の案は
「国主は独自のLINEアカウントで同じようにゲームを展開できる（横展開）」で、
将来的にはメタバースに統合し、現在の戦国パスポート自体も国主と同じ
ポジションになる、というもの。

その後の確認で **国主は独自決済を持たず、プロジェクト運営者（本部）が
運営したうえで「国主」というポジションを与える** ことが確定した。

---

## 設計上の注意点：世界を分けるとゲーム性が落ちる

国取りは「全国の他プレイヤーと同じ地図を奪い合う」から成立している。
世界を国主ごとに分けると各世界のプレイヤーは数十人規模になり、競争相手が
いなくなる。天下統一も「50人中1位」ではなく「20人中1位」になり価値が下がる。

**世界は1つのまま、国主にその中の「領地」を与える**ほうが、国主にとっても
魅力が高いと考えられる。「自分だけの小さな世界の王」より「全国が競い合う
1つの世界で美濃国を治める領主」のほうが誇れるため。

以下の案はすべてこの前提（世界は共通）に立つ。

---

## 案1：配下の城からの継続報酬 ★最有力

国主は、自国の城で土地が売れるたびに報酬を受け取る。城主が自分の城の売上から
報酬を得るのに対し、国主は**自国にあるすべての城**から得る。城主が増えるほど
国主の収入が増えるため、「上位プラン」の説明として最も分かりやすく、
プラン価格の根拠も立てやすい。

**実装は軽い。** 報酬エンジン `src/modules/castle/domain/commission-engine.ts` は
すでに受取区分を6種類持つ純粋関数として実装済みで、テストも揃っている。

```ts
export type RecipientType = "lord" | "agency" | "organization" | "hq" | "development_fund" | "regional_activity";
```

ここに `province_lord` を1つ足し、`CommissionRateSet` に料率を追加する。
DB非依存の関数なので、既存の TC1〜TC7 と同じ形でテストできる。

## 案2：城主の任命権と「城枠」

国主は自国に何城まで城主を置けるかの枠を持ち、城主候補を推薦・任命できる。

城主の「初期30区画」の販売枠（`plot_allocations`）と同じ構造を1段上に作る
（`castle_allocations` 相当）。国主は自分で城主を集める動機ができ、それが
そのまま案1の報酬に繋がる。

契約の状態管理は城主契約（`castle_lord_contracts` の9状態：
draft → screening → approved → payment_pending → training → active →
suspended / expired → terminated）と遷移マトリクスをそのまま流用できる。

## 案3：国のブランディングと国別ランキング

国旗・国名・国主からの布告（LINE配信）・国別ランキング。「美濃国 第3代国主」
のような称号、自国民の一覧、国別の貢献度ランキング。

`src/lib/line-push.ts` の個別push基盤があるため、国主が自国民だけに布告を出す
機能も作れる。金銭的リターンではなく名誉と実感を作る部分で、案1・2と
組み合わせると効く。

## 案4：独自LINE入口（同じ世界への専用入口）

国主専用のLINEアカウントを持つが、入った先は同じ戦国世界。国主が自分の顧客を
LINEで集め、そこから戦国パスポートに送客する。入口とブランディングは国主のもの、
世界は共通。ここから入ったユーザーは自動的にその国に所属する。

集客メリットを取りつつゲーム性を壊さない折衷案。ただし4案の中で最も工数が
かかり、**国主自身にLINE運用の負担が発生する**点は要検討。

---

## 工数の目安

| 案 | 内容 | 規模 | 既存資産の再利用 |
|---|---|---|---|
| 1 | 配下の城からの継続報酬 | 小 | 報酬エンジンに1区分追加 |
| 2 | 城主任命権・城枠 | 中 | 城主契約の状態機械を流用 |
| 3 | 国のブランディング・国別ランキング | 中 | LINE配信・ランキングを流用 |
| 4 | 独自LINE入口 | 大 | 設定の複数行化・入口判定が新規 |

案1と案2だけで「上位プラン」として成立する。案4がなくても、国主は
「配下の城主を増やすほど儲かる領主」という明確な立場になる。

## 参考：横展開（世界を分ける）を選ぶ場合のコスト実測

案4をさらに進めて世界ごと分離する場合に備え、2026-07-29 時点の
コードベースを実測した結果を記録しておく。

| 項目 | 実測値 |
|---|---|
| テーブル数 | 86 |
| DBアクセス箇所（`.from(`） | 498 |
| RPC呼び出し | 24 |
| DB関数（migration内） | 40 |
| APIルート | 192 |

### 有利な点

**DBアクセスが1関数に完全集約されている。** `createSupabaseServerClient()` を
使うファイルが177、`createClient` を直接呼ぶ箇所は **0**。接続先DBを切り替える
場合、書き換えるのは `src/lib/supabase-server.ts` の1ファイルで足りる。

**千ノ国ハブ連携基盤が完成済み。** `/api/integrations/sen-no-kuni-hub`、
`common_user_id`、`entitlements`、HMAC署名、Inbox/Outbox。「複数の独立した
システムが対等に繋がる」層はすでにある。

### 不利な点（世界を分ける場合の障害）

- `users.line_user_id` が**グローバルに unique**（`line_user_id text not null unique`）。
  同じ人が2つの国に登録できない。`(tenant_id, line_user_id)` への張り替えが必要
- 設定テーブル7つが**1行前提**の設計：`line_settings` / `gacha_config` /
  `payment_settings` / `castle_lord_plan_settings` / `ai_image_settings` /
  `metaverse_tour_settings` / `agency_integration_settings`
- 498箇所のクエリすべてに絞り込みが必要。絞り込み漏れ1箇所が他国のデータ露出になる

### 決済が本部一本なら、DBも一本にすべき

国主が独自決済を持たないことが確定したため、DBを国ごとに分ける方式は
以下の理由で不利になった。

1. **Stripeのwebhookは1つの宛先にしか届かない。** DBを分けると、届いた決済
   イベントを毎回振り分ける必要が出る。既存の冪等性・再実行の仕組みが複雑になる
2. **報酬元帳と本部ダッシュボードが分断される。** `commission_ledger` は
   1つのDBにある前提で作られている
3. **国主は本部が任命するポジション**なので、`castle_lord_contracts` と同じ
   構造の上位階層として作るのが自然
4. **最終的に統合するなら最初から統合しておくほうが安い。** 分けたものを後で
   1つにするのは、DB間のID衝突を解消しながらのデータ移行になる

## 未確定の論点（着手前に埋める必要がある）

1. **報酬配分** — 土地1件が売れたとき、本部・国主・城主・代理店・組織で何%ずつ
   分けるか。**これが決まらないと案1は実装できない**
2. **国主プランの価格** — 何城・何区画売れて回収できるかの試算
3. **国主になる条件** — 城主からの昇格か、直接申込か。実績要件・審査要件
4. **世界を分けるか否か** — 上記の注意点を踏まえた最終判断
5. **メタバース統合の意味** — 既存の `metaverse_*`（3D内覧・区画権利）に各国の
   エリアを持たせるのか、別々に育てた世界を後から統合するのか

## 次にやるとよいこと

案1の設計メモを1枚作る。現在の城主プランの報酬構造・価格設定・区画価格を
実際のコードから拾い、そこに国主を1段足すとどうなるかを試算した形にする。
配分が決まれば、実装自体は既存の報酬エンジンへの追加なので短期間で終わる。
