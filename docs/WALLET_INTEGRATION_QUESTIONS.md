# 1. 識別子 — `external_user_id` に何を送るか ★

**優先度: A**

## 質問 1-1

`POST /api/v1/rewards/plan` … ではなく `POST /api/v1/rewards/grant` のリクエストに
`common_user_id` を受け付ける予定はありますか。

## 背景

千ノ国パスポートの実装指示書§2(3)は「ユーザーの基準識別子には共通ID基盤の
`common_user_id` を使用する」と定めています。

一方、現在の `RewardGrantRequestSchema`（`packages/shared-types/src/api-schemas.ts`）には
`common_user_id` フィールドが無く、`service_code` + `external_user_id` の組で
アカウントを解決する設計と理解しています。

`OveAccount.common_user_id` という列はウォレット側に存在しますが、これはウォレットが
sengoku-ai.com の `POST /api/common-users/resolve` を**呼び出す側**として自分で解決・
保存するためのもので、外部サービスからの付与時の識別子ではない、という理解で合っていますか。

## 質問 1-2

合っている場合、千ノ国パスポートは `external_user_id` として何を送るべきですか。

こちらの案は **`users.id`（パスポート内部のuuid）** です。理由:

- 不変で、必ず存在する（`common_user_id` は外部HUBへの問い合わせに失敗すると解決できない）
- パスポート側で `common_user_id` は1ユーザー1件の一意制約があるため、後から共通IDへ
  寄せ直す必要が生じても対応関係が一意に決まる
- 255文字までの任意文字列という制約に収まる

## なぜ急ぐか

**一度送った `external_user_id` は後から変更できない**と理解しています
（未登録の `external_user_id` でアカウント・ウォレット・連携が自動作成され、以後その値で解決されるため）。
1件でも本番付与が走った後では変更に移行作業が必要になるので、**実証開始前に確定させたい**項目です。

## 回答が無い場合に当面置く前提

`external_user_id` = `users.id`。付与要求レコードには `common_user_id` も併記して保存し、
後から寄せ直せるようにしておく。

# 2. 既存付与の重複防止 — 取引履歴の照会手段 ★

**優先度: A**

## 質問 2-1

外部サービスから**取引履歴を照会するAPI**を追加する予定はありますか。

現状、外部サービスが呼べるのは
`GET /api/v1/service/accounts/{externalUserId}/balance` のみで、返るのは
`available_balance` / `pending_balance` / `held_balance` / `lifetime_credited` /
`lifetime_debited` といった**集計値**だけ、と理解しています。

取引履歴 `GET /api/v1/me/transactions` は OVE独自セッション認証の本人向けAPIで、
外部サービスからは呼べない（横断照会を防ぐ設計）という理解で合っていますか。

## 背景

パスポート側の実装指示書§8.4は、既存付与との重複を防ぐ手段として

1. Walletの取引履歴照会APIを `reasonType` / `reasonId` 等で検索する
2. 運営が提供する正式な付与済みデータを判定テーブルへ取り込む

の2案を挙げていますが、**現状の仕様では (1) が実現できません。**

## 質問 2-2

(1) を可能にする場合、以下のような形を想定しています。実現可能性と時期を教えてください。

```
GET /api/v1/service/accounts/{externalUserId}/transactions
  ?transaction_type=...&event_id=...&status=COMPLETED
```

- 認証は既存のHMAC署名と同じ
- **自サービスに紐づく `external_user_id` のみ**照会可（既存の残高照会と同じ制限）
- 返すのは自サービスが作った取引のみ、あるいは全取引か（どちらでも設計できます）

## 回答が無い場合に当面置く前提

指示書§8.4(2) を採用。運営から正式な付与済みデータ（出所・取込日時・更新履歴つき）を
受け取って判定テーブルへ取り込む。取込データが無い間は**付与を保留**する
（推測で付与済み判定を作らない）。

既存参加者への新規付与を**保留**する。対象者判定基準が確定するまで、

# 6. 付与API・冪等性の確認

**優先度: B**

以下は**理解の確認**です。合っていれば「合っている」だけで結構です。

## 質問 6-1

付与リクエストの形は以下で合っていますか。

```json
{
  "service_code": "SENGOKU_PASSPORT",
  "external_user_id": "<パスポート側のユーザーID>",
  "event_type": "MISSION_COMPLETION",
  "event_id": "<ミッション完了イベントID>",
  "amount": 1000,
  "transaction_type": "<5章で決定>",
  "display_name": "はじまりの旅 ミッション完了特典",
  "description": "<任意>",
  "idempotency_key": "mission_completion:<完了イベントID>"
}
```

## 質問 6-2

`idempotency_key` は **HTTPヘッダーではなくリクエストボディのフィールド**で、
同一キーの再送は新規取引を作らず**既存取引をそのまま返す**（エラーにならない）、
という理解で合っていますか。

代理店システム側のガイドが定める `Idempotency-Key` ヘッダー方式とは別規約、という点も確認したいです。

## 質問 6-3

`event_id` と `idempotency_key` の役割の違いを教えてください。

`per_event_limit` は `event_id` で判定されると理解しています。
「はじまりの旅」では**ミッション完了イベントIDを両方に使う**予定ですが、
それで問題ないでしょうか（1完了イベント = 1付与）。

## 質問 6-4

HMAC署名の対象文字列は

```
`${timestamp}.${nonce}.${method}:${path}:${JSON.stringify(body)}`
```

で、`method` は大文字、`path` はクエリ文字列を含むフルパス、`body` は Node.js の
`JSON.stringify` と完全一致（キー順序・非ASCII文字を**エスケープしない**）、
という理解で合っていますか。

パスポート側も Node.js（Next.js）なので `JSON.stringify` は一致するはずですが、
**署名生成の検証用に、正解の署名値が分かるテストベクタ**（ダミーの
signing_secret・timestamp・nonce・body と、そこから生成される署名文字列）を
いただけると、接続前に実装を検証できて助かります。

## 質問 6-5

`amount` / `balance_before` / `balance_after` はレスポンスで**文字列**として返る、
という理解で合っていますか（BigIntの精度対策）。

`packages/shared-types` の `TransactionResponseSchema` では `z.number()` になっている一方、
`docs/EXTERNAL_DEVELOPER_GUIDE.md` 8.1章の例では `"amount": "10000"` と文字列になっており、
**スキーマとドキュメントが食い違って見えます。** どちらが正でしょうか。

# 付録: 現時点の理解のまとめ

こちらが読み取った内容です。誤りがあれば指摘してください。

| 項目 | 理解 |
|---|---|
| エンドポイント | `POST /api/v1/rewards/grant` / `POST /api/v1/transactions/debit` / `POST /api/v1/transactions/{id}/reverse` / `GET /api/v1/service/accounts/{externalUserId}/balance` |
| 認証 | HMAC-SHA256。`X-OVE-Api-Key` / `X-OVE-Timestamp` / `X-OVE-Nonce` / `X-OVE-Signature` |
| タイムスタンプ許容 | ±5分 |
| nonce | 連携先ごとに一度きり（リプレイ拒否） |
| 冪等キー | **ボディのフィールド**。再送は既存取引を返す。255文字まで |
| サービスコード | `SENGOKU_PASSPORT`（enum定義済み） |
| アカウント自動作成 | 未登録の `external_user_id` で自動作成される |
| 取引履歴照会 | **外部サービス向けは無い**（残高の集計値のみ） |
| `common_user_id` | 付与APIは受け付けない |
| 台帳の訂正 | 直接UPDATE/DELETEせず、必ずREVERSALで記録 |
| エラー形式 | `{ ok, error: { code, message }, request_id }`（残高照会とSSOのみ旧形式） |
| APIキー発行 | 運用担当者の手動作業のみ |
| 旧3,000 OVE | `wallet_referral_benefits` に `PENDING` で作成。**確定付与は未実装** |
