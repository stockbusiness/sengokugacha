## 2. HMAC 仕様 — PR5-b で間違えやすい3点

Wallet 側から `docs/EXTERNAL_DEVELOPER_GUIDE.md` 4.1章が転記されました。前回より踏み込んだ記載があり、**実装で取り違えると全リクエストが401になる**箇所が3つあります。

| # | 項目 | 仕様 | 誤りやすい点 |
|---|---|---|---|
| 1 | `X-OVE-Timestamp` | **UNIX エポック「ミリ秒」** | 秒で実装すると、±5分の判定を必ず外れて401 |
| 2 | `path` | **クエリ文字列を含むフルパス** | パス部分だけで署名すると不一致 |
| 3 | `body` | **Node.js の `JSON.stringify` と完全一致**（キー順序・非ASCIIのエスケープを含む） | 署名用にオブジェクトを組み直すと壊れる。**送信する raw body そのものから署名を作る**必要がある |

確定仕様（PR5-b の実装根拠として固定）:

```
X-OVE-Api-Key:    ovk_...
X-OVE-Timestamp:  <UNIXエポックミリ秒>
X-OVE-Nonce:      <リクエストごとに変わるランダム文字列>
X-OVE-Signature:  HMAC-SHA256(signing_secret,
                    `${timestamp}.${nonce}.${METHOD}:${fullPath}:${rawBody}`)
```

- 時刻許容ずれ: ±5分（超えると401）
- nonce: 連携先ごとにワンタイム。再利用で401
- `signing_secret` は**発行時にのみ平文で渡される**。Wallet 側でもハッシュ・暗号化保存のみで再取得不可

3 の帰結として、**PR5-b の HTTP アダプタは「本文をシリアライズしてから署名し、その同一文字列を送信する」構造にする必要があります。** 署名と送信で別々に `JSON.stringify` を呼ぶ実装は避けます。

## HMAC 仕様 — 受領しました

`docs/EXTERNAL_DEVELOPER_GUIDE.md` 4.1章の転記、ありがとうございました。実装の根拠として、以下の3点を特に確認しました。

1. **`X-OVE-Timestamp` は UNIX エポック「ミリ秒」**（秒ではない）
2. **`path` はクエリ文字列を含むフルパス**
3. **`body` は Node.js の `JSON.stringify` と完全一致させる**（キー順序・非ASCIIのエスケープを含む）

3 については、**署名対象の文字列と実際に送信する本文が同一になる実装**にします（署名用と送信用で別々にシリアライズしない）。齟齬が出やすい箇所と認識しています。

### ただし、文章の転記だけでは確定させません

HMAC は「読めば分かるが、実装すると1バイト単位でずれる」типの仕様です。文章で合意できていても、実際に署名が通るかは別問題です。

**次の11ケースについて、入力と期待される署名（または期待される応答）を固定した fixture をご提供いただけないでしょうか。** こちらで同じ fixture を通し、双方の実装が一致することを確認したうえで実送信へ進みます。

| # | ケース | 確認したいこと |
|---|---|---|
| 1 | 通常の付与リクエスト | 基本の署名一致 |
| 2 | `timestamp` がミリ秒であること | 秒で送った場合に拒否されること |
| 3 | クエリ文字列を含む `fullPath` | クエリを含めない場合に拒否されること |

## 上限値 — 決定しました

運営側で次のとおり決定しました。`reward_rules` 行の登録をご依頼します。

| 項目 | 値 |
|---|---|
| 1回あたり最大 | **3,000 OVE** |
| 1ユーザーあたり累計最大 | **3,000 OVE** |
| 同一ミッションの付与 | **1回まで** |
| 累計の管理単位 | `rule_code` 単位、`external_user_id` 単位 |
| OVE残高の有効期限 | **無期限** |

**3,000 OVE は「1回で付与できる最大値」であり、通常額ではありません。** 「はじまりの旅」の付与総額が3,000 OVE で、これを複数のミッションに分けて段階付与します。ミッション構成が固まり次第、1回あたりの通常付与額はこれより低い値へ設定します。

### 有効期限についてのご相談

**OVE残高そのものは有効期限なしとしたい**というのが運営の決定です。

`reward_rules` が有効期限日数を**必須項目**としている場合、こちらで任意の期限を設定することは避けたいと考えています。期限を切ると、後から「無期限」へ戻す際に既存残高の扱いが問題になるためです。

**「無期限」を表現できる方法（null 許容、あるいは特別な値）をご教示いただけないでしょうか。** 現時点で仕様に無い場合は、追加をご検討いただきたく思います。

### fail-closed の方針

こちら側は次をすべて**付与拒否**として実装します。

- `reward_rules` が未登録
- 上限が未設定
- 上限を超過

自動再送時も累計上限を再確認し、同じ `idempotency_key` では二重付与しません。**一括遡及付与は行いません。**

ご指摘いただいた「`reward_rules` 行の登録前は上限なしで付与できてしまう」という状態で送信を始めることはありません。
