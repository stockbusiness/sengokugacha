## 1. 満たしている項目

### 1.1 管理者権限（項目1）

`src/app/api/admin/payouts/route.ts`

```ts
if (!(await requireManagerRole())) {
  return NextResponse.json({ error: "支払処理は本部管理者のみ実行できます" }, { status: 403 });
}
```

`getAdminSession()` による認証（401）の後に、`requireManagerRole()` で本部管理者を要求（403）しています。operator は実行できません。

### 1.2 確認ダイアログ（項目2）

`src/app/admin/(dashboard)/castle-payouts/page.tsx:62`

```
「〇〇さんへ 12,345円を支払済みにしますか?(実際の振込は別途行ってください)」
```

受取者名と金額が入り、実振込ではないことも明記されています。

### 1.3 実行者と実行日時（項目5）

`payouts` 行に `created_by: actorName` と `paid_at: nowIso` を記録し、同じ時刻を `commission_ledger.paid_at` にも入れています。

### 1.4 paid済み行の再処理禁止（項目7）

対象の抽出条件が

```ts
.eq("status", "confirmed")
.is("payout_id", null)
```

のため、`status = 'paid'` の行と、既に payout に紐づいた行は対象外です。対象0件なら 400 で止まります。

## 2. 欠落と注意点

### 2.1 項目3：二重実行防止 — サーバー側に競合の窓があります ⚠️

**画面側の連打は防げています。** `payingKey` によりボタンが `disabled` になります。

**しかしサーバー側に排他がありません。** 同じ受取者に対する2つのリクエストがほぼ同時に届くと、次の順で進行しえます。

| 時刻 | リクエストA | リクエストB |
|---|---|---|
| 1 | 確定済み・未払いを SELECT（3件） | |
| 2 | | 同じ3件を SELECT（Aはまだ更新していない） |
| 3 | `payouts` に INSERT | |
| 4 | | `payouts` に INSERT |
| 5 | `commission_ledger` を UPDATE | |
| 6 | | 同じ行を UPDATE（`payout_id` が後勝ち） |

結果、**`payouts` に同じ支払が2行でき、支払総額が二重に計上されます**。`commission_ledger` 側は後勝ちで1つの payout にしか紐づかないため、**payouts の合計と ledger の合計が食い違う**状態になります。

実際の振込は画面外で行うため送金は二重になりませんが、**清算の記録が壊れます**。Passport は移管前報酬の清算専用なので、記録の正確さがこの画面の存在意義そのものです。

再現条件は「同一受取者への同時実行」で、ブラウザの二度押しでは起きにくいものの、タブを2つ開く・通信リトライ・複数の管理者が同時に操作、で起こりえます。

**修正案**：`purchase_grant_steps` や `integration_outbox_events` で既に使っている claim/fencing と同じ考え方で、受取者単位の排他を1つ入れます。最小の実装は、対象抽出を `select ... for update` を伴うDB関数へ移し、INSERT と UPDATE を同一トランザクションに収めることです。

### 2.2 項目4：対象件数が表示されていません ⚠️

確認ダイアログに出るのは**受取者名と金額のみ**で、**何件の報酬明細をまとめるのかが出ていません**。

「3件・12,345円」と「30件・12,345円」は運用上まったく違う意味を持ちます。件数が無いと、確定漏れや二重確定に気づく機会が失われます。

**修正案**：一覧と確認ダイアログの両方に件数を出します。一覧APIが返す情報に件数を含める小さな変更です。

### 2.3 項目6：監査ログは出るが、失敗しても気づけません

`logAdminAction(actorName, "payout_create", "payout_id=... total_amount_yen=...")` を記録しています。項目としては満たしています。

ただし **`logAdminAction()` はすべての例外を握り潰します**（`console.error` のみ）。監査ログの書き込みに失敗しても支払記録は成功し、**呼び出し側は失敗に気づけません**。

これは C6 の調査で私が判断を誤った原因でもあります（「記録が無い＝処理が走っていない」と考えましたが、記録が落ちただけの可能性を排除できていませんでした）。

支払は金銭に関わる操作なので、**監査ログの失敗を握り潰さない**（少なくとも警告として応答に含める）ほうが妥当だと考えます。ただし「監査ログが書けないと支払記録も失敗する」設計にすると、逆に業務が止まります。**応答に `auditLogged: false` を含める**程度の扱いを提案します。

## 3. ご判断いただきたいこと

現状 `commission_ledger` は0件で、**急いで直す必要はありません**。ご指示の「新しい成果や報酬を作成・加算する操作は追加しない」にも抵触しません（いずれも記録の正確さを守る変更です）。

| 案 | 内容 |
|---|---|
| **(A)** | 別PR（PR-P1d）として、§2.1 の排他と §2.2 の件数表示を直す。§2.3 は応答へ `auditLogged` を足すだけ |
| (B) | §2.2 の件数表示だけ直し、§2.1 は「移管前報酬の清算が始まる前に対応」として保留する |
| (C) | 現状のままとし、清算開始前に改めて判断する |

**(A) を推奨します。** いま `commission_ledger` が0件で、**壊れる対象が存在しないうちに直せる**ためです。清算が始まってから同時実行で記録が食い違うと、どちらが正しいかを事後に判定する作業が発生します。

いずれの案でも、**PR-P2b とは独立**して進められます。
