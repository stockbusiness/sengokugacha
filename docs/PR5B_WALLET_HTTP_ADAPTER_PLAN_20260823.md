## 3. HMAC 署名

### 3.1 仕様（Wallet 提供の `EXTERNAL_DEVELOPER_GUIDE.md` 4.1章）

| 項目 | 内容 |
|---|---|
| ヘッダ | `X-OVE-Api-Key` / `X-OVE-Timestamp` / `X-OVE-Nonce` / `X-OVE-Signature` |
| 署名対象 | `` `${timestamp}.${nonce}.${METHOD}:${fullPath}:${rawBody}` `` |
| `timestamp` | UNIX エポック **ミリ秒**（秒ではない） |
| 許容ずれ | ±5分 |
| `nonce` | 一度きり |
| `fullPath` | **クエリ文字列を含む** |
| `rawBody` | Node の `JSON.stringify` と**完全一致** |

### 3.2 実装上の要点

**送信する raw body と署名対象の body を、同じ1つの文字列にします。**

```ts
const rawBody = JSON.stringify(payload);   // ここで1度だけ文字列化する
const signature = sign(timestamp, nonce, method, fullPath, rawBody);
await fetch(url, { method, headers, body: rawBody });  // 同じ文字列をそのまま送る
```

署名用と送信用で別々に `JSON.stringify` を呼ぶと、キー順序が同じでも**実装やバージョンの差で1バイトずれる**ことがあります。構造テストで「`JSON.stringify` の呼び出しが1箇所であること」を機械的に担保します。

### 3.3 文章の転記では確定させません

**ここが本PRで最も慎重を要する部分です。**

HMAC は「読めば分かるが、実装すると1バイト単位でずれる」仕様です。文章で合意できていても、実際に署名が通るかは別問題です。ご指示のとおり、**Wallet 側の公式ガイドと契約テスト fixture を正**とします。

### 【2026-09-07 確定】署名方式が変更されました

Wallet 側が **2026-09-07 に署名検証を「実際に送信されたボディそのもの」方式へ変更**しました。
こちらは未実装だったため手戻りはありません。

| 項目 | 確定内容 |
|---|---|
| **空 body** | **`""`（空文字）**。`"{}"` ではない |
| キー順序・整形・非ASCIIのエスケープ | **どれでもよい**。Wallet 側で正規化・再整列はしない |
| `timestamp` | UNIX エポック**ミリ秒13桁** |
| `path` | エンコード済みフルパスを**再エンコードせず**そのまま |

守るべきは1点だけです。**ボディの文字列を1回だけ組み立て、その文字列に署名し、その同じ文字列を送信する。**

**fixture は12ケース分が Wallet 側に存在**します（`docs/fixtures/hmac-auth-contract-fixtures.json`）。
各ケースに実際の送信文字列が `rawBody` として入っており、Wallet 側の実装と自動テストで
継続的に突き合わせているため乖離しません。返信で提供を依頼しています。

## 4. 上限の fail-closed

ご判断 §12 で確定した値です。

| 項目 | 値 |
|---|---|
| 1回あたり最大 | 3,000 OVE |
| 1ユーザーあたり累計最大 | 3,000 OVE |
| 同一ミッションの付与 | 1回まで |
| 累計の管理単位 | `rule_code` 単位、`external_user_id` 単位 |
| OVE残高の有効期限 | 無期限 |

3,000 OVE は「1回で付与できる最大値」であり通常額ではありません。ミッション構成確定後、通常付与額はこれより低い値へ設定します。

### 4.1 拒否する条件

次はすべて**付与拒否**（送信しない）です。

| 条件 | 理由 |
|---|---|
| `reward_rules` が未登録 | 上限が効いていない状態で送らない |
| 上限が未設定 | 同上 |
| 上限を超過 | — |
| 累計が上限に達している | — |

**判定は送信の直前に行い、自動再送のたびに再評価します。** 「1回目の判定結果を持ち回る」設計にすると、再送までの間に累計が変わった場合に上限を超えます。

同じ `idempotency_key` では二重付与しません（PR5-a の仕組み）。**一括遡及付与は行いません。**

### 4.2 上限判定は Passport 側と Wallet 側の両方で効きます

Passport 側の判定は「明らかに送ってはいけないものを送らない」ための一次防壁で、**正本は Wallet 側の `reward_rules`** です。両方が独立に効く状態を維持します。片方だけに寄せると、もう片方の設定漏れに気づけません。

## 5. 応答喪失の解決 — 単発照会

### 5.1 何が問題か

送信したが応答が返ってこなかった場合、**付与されたのかどうかが分かりません**。ここで再送すると二重付与の危険があり、放置すると未付与のまま残ります。

PR5-a の Fake アダプタには `lost_response` シナリオを用意し、状態機械が二重付与しないことは確認済みです。ただし**実際にどちらだったかを判定する手段は未実装**でした。

### 5.2 設計

`idempotency_key` で Wallet へ**単発照会**し、取引の有無を確認してから次を決めます。

| 照会結果 | 次の動作 |
|---|---|
| 取引が存在する | **成功として確定**する（再送しない） |
| 取引が存在しない | 再送する |
| 照会自体が失敗 | 状態を変えず、次回の再試行へ委ねる |

**照会が失敗したときに「存在しない」と扱わないことが要点です。** そこを誤ると二重付与になります。

**【2026-09-07 確定】** パスは次のとおりです。

```
GET /api/v1/service/transactions/by-idempotency-key/{idempotency_key}
```

必要な scope は `transactions.read` で、**Wallet 側が接続開始前に付与**します（こちらの作業なし）。

## 6. CSV 照合

### 6.1 目的

Go 条件の「照合で差異0件」を満たすための突合です。Passport 側の送信記録と Wallet 側の取引記録を突き合わせ、次を検出します。

| 検出したいもの | 意味 |
|---|---|
| Passport にあり Wallet に無い | 送ったつもりで届いていない |
| Wallet にあり Passport に無い | 二重付与、または他経路からの付与 |
| 金額の相違 | どちらかの記録が誤っている |

### 6.2 【2026-09-07 確定】10,000件超過はページングで扱います

Wallet 側の仕様が判明しました。**黙って切り捨てない作り**になっています。

```
GET /api/v1/service/transactions/export
  ?period_from=...&period_to=...&rule_code=...&cursor=...
```

| 項目 | 仕様 |
|---|---|
| 期間上限 | **92日**。超えると 400 |
| 1応答の上限 | **10,000件** |
| 続きの有無 | 応答ヘッダー `X-Has-More: true` |
| 続きの取得 | `X-Next-Cursor` の値を次回の `cursor` へ渡す |
| 範囲 | 自社が付与・利用した取引のみ |

したがってこちらは、**カーソルを最後まで辿る実装**にします。ご指示の「10,000件超過を検知する」は、
**`X-Has-More` が `true` のまま処理を終えないこと**として実装します。1ページだけ読んで
終える実装は、超過分の差異を永久に検出できません。

必要な scope は `transactions.export` で、Wallet 側が付与します。

## 9. 機能フラグは OFF のまま

ご指示 §13 のとおり、本番の機能フラグは**別途 Go 承認まで OFF** を維持します。

PR5-a では**二重の承認**を要求する形にしています。

1. DB の `learning_journey_settings.rewards_enabled`
2. コード上の定数 `WALLET_HTTP_ADAPTER_ALLOWED = false`

**両方が開かないと実送信は起きません。** DB のフラグを誤って ON にしても、コード側が閉じている限り送信されません。本PRでもこの二重化を維持します。

`WALLET_HTTP_ADAPTER_ALLOWED` を `true` にするのは、§10 の Go 条件がすべて満たされ、改めてご承認をいただいた後の**別PR**とします。

### 10.1 `common_user_id` 未解決の19名について

ご指示 §5 のとおり、次は**行いません**。

- `users.id` を暫定的に `external_user_id` として送信する
- メールアドレスや LINE ID を代替識別子として送信する
- **未解決の `common_user_id` を推測して紐付ける**
- Agency との接続前に既存19名を自動統合する

**代理店システム側で解決されるまで、本番送信を開始しません。**

なお `external_user_id` は Wallet 専用の新規 UUID を Passport が発行する方式で合意済みのため、**識別子そのものは `common_user_id` の解決を待たずに発行できます**。ただし「誰に対する識別子か」を確定するには `common_user_id` の解決が要るため、Go 条件1は依然として前提です。
