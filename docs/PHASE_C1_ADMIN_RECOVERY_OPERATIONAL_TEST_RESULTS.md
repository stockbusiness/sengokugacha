# 千ノ国パスポート 管理画面復旧操作の実機確認結果(§5.9)

区分: 1.ソースコード確認済み / 2.local確認済み / **3.staging確認済み** / 4.production未確認 / 5.未対応 / 6.問題あり / 7.管理者操作待ち / 8.Stripeアカウント待ち

Stripe取得待ち期間対応指示書§5.9に基づき、2026-07-28に`stockbusiness`が`/admin/integration-recovery`から実際の復旧操作を実行して確認した。

## 前提

`purchases`・`entitlements`関連の復旧セクション(購入権利付与再実行、entitlement再解決)は該当テーブルが空(§5.3で確認済み)のため今回対象外。実データが存在した唯一のセクションである「common_user_id未解決ユーザー」(§5.7で新規実装)を対象に、架空データではなく実際に9件存在する未解決ユーザーへ実機で操作した。

## 実測結果

### 個別「再解決」ボタン

1件のユーザーに対して個別の「再解決」ボタンを押した結果、`再解決結果: in_progress`が返った。これは直前に別のリクエスト(後述の全件再試行)がこのユーザーを既にclaim中だったための正常な排他制御の結果であり、二重解決・競合が発生していないことを示す。

### 「全件再解決を試行」ボタン(9件対象)

実行結果: `9件を再試行し、0件解決しました。`

`common_user_resolution_attempts`テーブルを確認したところ、対象9件全てで以下を確認できた。

- `attempt_count`が2(初回のLINEログイン時の失敗+今回の再試行)に増加している
- `last_error`が`resolveCommonUserId returned null`(sengoku-ai.com側に該当ユーザーの情報がまだ無く、解決不能という正直な結果。例外やエラーではない)
- `lease_expires_at`が確認時点で既に過去の時刻になっており、リースが正しく解放されextit(次回再試行や他のリクエストがブロックされない状態)であることを確認

## 結論

- 個別・全件どちらの復旧操作も、claim/lease方式の排他制御・エラー記録・DB状態の整合性を含めて設計通り動作することを実機で確認した。
- 今回の実行では9件とも「未解決のまま」という結果になったが、これは機能の不具合ではなく、外部システム(sengoku-ai.com)側の現状のデータ状況を反映した正直な結果である。該当ユーザーの情報がsengoku-ai.com側で整い次第、同じボタンで再試行すれば解決される見込み。
- `purchases`・`entitlements`系の復旧操作(再試行・再解決)は実データが存在しないため今回未確認。Stripe接続後、実際の決済・権利付与が発生した段階で改めて確認することを推奨する。
