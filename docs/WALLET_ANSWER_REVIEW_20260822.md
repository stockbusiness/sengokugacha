## 4. 【判断待ち①】`external_user_id` に何を送るか

### 状況

Wallet の回答は次のとおりで、**判断はこちらに委ねられています**。

> Wallet側は値の意味・形式に関与しません。貴サービス内でユーザーを一意に指せる安定した識別子であれば、形式は問いません。
> ただし `users.id`（内部DB主キー）をそのまま送る運用にするかどうかは、貴社側のID設計判断です。**Wallet側からの指定・推奨はありません。**

### 使えない選択肢

| 候補 | 可否 | 理由 |
|---|---|---|
| `users.id` | **禁止** | 8/22 ご指示3。指示書 禁止1「一度作成されたWallet口座との紐付け変更が困難になる」 |
| `common_user_id` | **不可** | 付与APIが受け付けない。かつ本番19名全員が未解決 |
| メール / LINE ID | **禁止** | 8/22 ご指示3 |

### 提案する方針

**Wallet 連携専用の識別子を新規に発行する。**

`users` に列を1本追加し（例: `wallet_external_user_id uuid unique`）、Wallet へ初回送信する時点で採番して固定します。

**この方式を推す理由**

- `users.id` とは別の値なので、ご指示3の禁止事項に抵触しません
- Wallet 側は「値の意味・形式に関与しない」ため、UUID で問題ありません
- 将来 `common_user_id` 方式へ移行する際、**Wallet 口座との紐付けを壊さずに済みます**。Wallet 口座は `external_user_id` に紐づくので、この値さえ変えなければ移行時も同じ口座を指せます
- 内部主キーを外部へ出さないので、`users.id` の推測・列挙のリスクもありません

**この方針でよいか、ご判断ください。** 決まれば PR5-b の前提が1つ埋まります。列の追加は PR5-b のマイグレーションに含めます。

## ■1 利用者識別子 — ご提案を受け入れます

**「既存の `external_user_id` 方式でスタートし、`common_user_id` 対応は方針確定後に別PRで追従」という進め方で問題ありません。**

送信する `external_user_id` については、こちらで次のとおり決定しました。

- **`users.id`（内部DB主キー）は送りません。** Wallet 口座と一度紐づくと変更が困難になるため、内部主キーを外部識別子に流用しない方針です
- **Wallet 連携専用の識別子を新規に発行**し、初回送信時に採番して以後固定します（形式は UUID）
- この値は将来 `common_user_id` 方式へ移行する場合も変更しません。Wallet 口座との紐付けを壊さないためです

なお、こちらでは `common_user_id` が現時点で全利用者について未解決の状態です（別システムとの連携が未接続のため）。**この点からも、当面は `external_user_id` 方式が唯一の選択肢**となります。

## ■2 学習ミッション専用の取引区分 — 確認しました

`LEARNING_JOURNEY_REWARD` / `SENGOKU_LEARNING_JOURNEY_REWARD` の追加、ありがとうございます。こちらの実装でも同じ値を使う前提になっており、一致を確認しました。

**`service_code` について1点確認させてください。** こちらは `SENGOKU_PASSPORT`（`ServiceCode` enum の値）をそのまま送る想定で合っていますか。

**上限値のご指摘、ありがとうございます。** 「`reward_rules` 行の登録前は上限なしで付与できてしまう」という点は、こちらの受入条件（Passport・Wallet 双方の上限が有効であること）に直接関わります。

**具体的な上限値が確定次第、Wallet運用担当者へご連携します。** 確定するまでは、こちら側の送信機能を無効のまま維持します。

## ■3 取引照合 — 要件をお伝えします

4点の質問に回答します。

| 質問 | 回答 |
|---|---|
| 照合の頻度 | **日次1回**で合っています |
| 方式の希望 | **CSV（バッチダウンロード）を第一希望**とします。日次1回・全件突合という用途にはページングよりCSVが扱いやすいためです。API のみの提供になる場合もそれで問題ありません |
| 必須の絞り込み | **period + service_code + rule_code** をお願いします。rule_code は「はじまりの旅」の取引だけを抽出するために必要です |
| 単発照会 | **`idempotency_key` での単発照会を希望**します。応答喪失時に「Wallet 側に取引が成立しているか」を確認する手段が必要なためです。`event_id` は不要です |
| 認証 | **既存のHMAC（`ExternalApiAuthGuard`）の流用を希望**します。新しい scope を切る必要があれば、そちらでも構いません |

CSV に含めていただきたい項目は、**取引ID / `idempotency_key` / `external_user_id` / 金額 / `transaction_type` / `rule_code` / 取引日時 / 状態（成立・取消）**です。こちら側の記録と1対1で突合できれば足ります。
