## お願い1: HMAC の固定 fixture をご提供ください

`EXTERNAL_DEVELOPER_GUIDE.md` 4.1章の転記、ありがとうございました。実装の根拠として、次の3点を特に確認しています。

1. `X-OVE-Timestamp` は UNIX エポック**ミリ秒**（秒ではない）
2. `path` は**クエリ文字列を含むフルパス**
3. `body` は Node.js の `JSON.stringify` と**完全一致**（キー順序・非ASCIIのエスケープを含む）

3 については、**署名対象の文字列と実際に送信する本文が同一になる実装**にします。署名用と送信用で別々にシリアライズしないという意味で、こちらの構造テストで「文字列化の呼び出しが1箇所であること」を機械的に担保する予定です。

### ただし、文章の転記だけでは確定させません

上記3点は理解しましたが、**文章からの読み取りを実装の正とはしません。** 貴社の公式ガイドと、**双方で共有する固定 fixture による契約テスト**を正としたいと考えています。

HMAC は「読めば分かるが、実装すると1バイト単位でずれる」種類の仕様です。文章で合意できていても、実際に署名が通るかは別問題です。

**次の11ケースについて、入力と期待される署名（または期待される応答）を固定した fixture をご提供いただけないでしょうか。**

| # | ケース | 確認したいこと |
|---|---|---|
| 1 | 通常の付与リクエスト | 基本の署名一致 |
| 2 | `timestamp` がミリ秒であること | 秒で送った場合に拒否されること |
| 3 | クエリ文字列を含む `fullPath` | クエリを含めない場合に拒否されること |
| 4 | 送信 raw body と署名対象 body がバイト単位で同一 | 別々にシリアライズした場合に拒否されること |
| 5 | 日本語を含む payload | 非ASCIIのエスケープ方式の一致 |
| 6 | **空 body** | **空文字として署名するのか、`{}` として署名するのか** |
| 7 | キー順序 | 順序が変わると署名が変わることの確認 |
| 8 | nonce 再利用 | 2回目が拒否されること |
| 9 | 許容時刻の範囲外（過去側・未来側） | 拒否されること |
| 10 | 署名不一致 | 拒否されること |
| 11 | 正常系が 2xx になること | 偽陰性でないことの確認 |

**6 と 7 は、いただいた文章からは一意に読み取れませんでした。** 特に**空 body の署名対象文字列**をご教示ください。

fixture のご提供が難しい場合は、staging に対してこちらから上記を実際に叩き、結果を突き合わせる形でも構いません。その場合は staging の接続情報をご手配ください（**署名鍵の値はこちらへ送らず**、貴社側の設定として投入していただく形で結構です）。

## お願い2: 報酬上限が確定しました — `reward_rules` の登録をお願いします

運営側で次のとおり決定しました。

| 項目 | 値 |
|---|---|
| 1回あたり最大 | **3,000 OVE** |
| 1ユーザーあたり累計最大 | **3,000 OVE** |
| 同一ミッションの付与 | **1回まで** |
| 累計の管理単位 | `rule_code` 単位、`external_user_id` 単位 |
| OVE残高の有効期限 | **無期限** |

**3,000 OVE は「1回で付与できる最大値」であり、通常額ではありません。** 「はじまりの旅」の付与総額が 3,000 OVE で、これを複数のミッションに分けて段階付与します。ミッション構成が固まり次第、1回あたりの通常付与額はこれより低い値へ設定します。

### 有効期限についてのご相談

**OVE残高そのものは有効期限なし**というのが運営の決定です。

`reward_rules` が有効期限日数を**必須項目**としている場合、こちらで任意の期限を設定することは避けたいと考えています。**期限を切ると、後から「無期限」へ戻す際に既存残高の扱いが問題になる**ためです。

「無期限」を表現できる方法（null 許容、あるいは特別な値）をご教示いただけないでしょうか。現時点で仕様に無い場合は、追加をご検討いただきたく思います。

### こちら側は fail-closed で実装します

次はすべて**付与拒否**（送信しない）とします。

- `reward_rules` が未登録
- 上限が未設定
- 上限を超過
- 累計が上限に達している

判定は送信の直前に行い、**自動再送のたびに再評価**します。同じ `idempotency_key` では二重付与しません。**一括遡及付与は行いません。**

ご指摘いただいた「`reward_rules` 行の登録前は上限なしで付与できてしまう」という状態で送信を始めることはありません。
