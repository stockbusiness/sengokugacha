## ③ 回帰テスト

### 重要な前提：IDトークン検証はSDKに依存しない

`src/lib/line.ts` の `verifyLineIdToken()` は、LINEの公開エンドポイント
`https://api.line.me/oauth2/v2.1/verify` に **サーバー側から** POSTして検証している。
LIFF SDKは一切関与しない。

```ts
const res = await fetch("https://api.line.me/oauth2/v2.1/verify", {
  method: "POST",
  headers: { "Content-Type": "application/x-www-form-urlencoded" },
  body: new URLSearchParams({ id_token: idToken, client_id: channelId }),
});
```

したがって **SDKのバージョン更新がIDトークン検証の挙動を変えることは原理的に無い。**
SDKが影響しうるのは「クライアント側でIDトークンを取得できるか」までである。

### 自動検証（実施済み・全通過）

| 項目 | 結果 |
|---|---|
| `npx tsc --noEmit` | 通過（使用中APIの型が2.29.2で維持されていることを確認） |
| `npm run lint` | 通過（既存warning 2件のみ） |
| 単体テスト 272件 | 通過 |
| アーキテクチャテスト 56件 | 通過 |
| `npm run build` | 通過 |

### 実機で必要な確認（サンドボックスからは実行不可）

LINEアプリ内でしか動作しないため、以下は実機での確認が必要。

| # | 確認項目 | 期待結果 |
|---|---|---|
| 1 | LINEアプリからLIFFを開く（初回・未ログイン） | LINEログイン画面へ遷移し、承認後に元のページへ戻る |
| 2 | ログイン済みで再度開く | ログイン画面を経由せず即座に表示される |
| 3 | リッチメニューからサブページ（例: `/gacha`）へ直接遷移 | ホームを経由せずログインが確立し、そのページが表示される |
| 4 | 紹介リンク（`?ref=CODE`）付きで開く | LINE認証から戻った後も `ref` が保持され、新規登録時に紹介元が記録される |
| 5 | サイドメニューからログアウト | LIFF・サーバー両方のセッションが破棄され、`/` へ戻る |
| 6 | ログアウト後に再ログイン | 同一アカウントでログインでき、石高・武将等のデータが保持されている |

**特に③と④は今回のSDK更新で影響を受けうる箇所**です。`liff.login()` のリダイレクト後に
元のURL（クエリ含む）へ戻る挙動に依存しているためです。

なお `ensure-liff-session.ts` には、サーバーセッションが有効ならIDトークン再検証を
スキップする実装が入っています。LIFFのIDトークンはセッションCookieより先に期限切れに
なることがあるためで、②の「ログイン済みで再度開く」がこの経路を通ります。

## ④ 課金機能の一覧

`purchases.item_type` のCHECK制約に定義されている5種類が、この実装が扱う課金の全体。

| item_type | 内容 | 実装状況 | 決済経路 |
|---|---|---|---|
| `kokudaka` | 石高パック | **実装済み・稼働可能** | Stripe Checkout |
| `gacha_ticket` | ガチャ券パック | **実装済み・稼働可能** | Stripe Checkout |
| `tenka_pass` | 天下パス | **定義のみ**。作成コードは存在しない | 未定 |
| `land_plot` | 城の土地区画 | **画面・API実装済み、購入ボタン未接続**（法務確定待ち） | Stripe Checkout（`castle-plot-checkout`） |
| `castle_lord_plan` | 城主プラン | **定義のみ**。作成コードは存在しない。現状は管理画面で契約を手動作成する運用 | 未定 |

### 補足

- 実際にユーザーが購入できるのは現時点で **`kokudaka` と `gacha_ticket` の2つだけ**
- ただし `payment_settings` が未設定のため、**本番では決済自体がまだ動作しない**
- 城主プラン（100万円）の販売は、アプリ内課金ではなく**代理店経由の対面手続き**
- **LINEアプリ内課金（LINEの課金基盤）は一切実装していない。** 決済はすべてStripe

## ⑤ 「現実の商品・サービス」と「デジタルコンテンツ」の分類

LINEミニアプリ／LIFFアプリでは、**デジタルコンテンツの販売にLINEのアプリ内課金の
利用が求められる場合がある**一方、現実の商品・サービスは対象外とされる。この観点での分類。

### デジタルコンテンツ（アプリ内課金の対象になりうる）

| item_type | 内容 | 判断理由 |
|---|---|---|
| `gacha_ticket` | ガチャ券パック | アプリ内でのみ消費され、アプリ内の武将カード取得にしか使えない。**最も明確にデジタルコンテンツ** |
| `kokudaka` | 石高パック | アプリ内のゲーム内通貨。現実の価値と交換されない |
| `tenka_pass` | 天下パス（未実装） | 内容次第だが、名称から見てアプリ内の機能解放と推測される |

### 判断が分かれるもの

| item_type | 内容 | 論点 |
|---|---|---|
| `land_plot` | 城の土地区画 | **「土地が提供する具体的な利用権」が未確定**（既存の法務ブロッカー）。現実の土地の権利を伴うなら現実のサービス、アプリ内の表示上の所有に留まるならデジタルコンテンツ。**この確定が分類を決める** |
| `castle_lord_plan` | 城主プラン | 城の運営参加権・販売枠の付与・研修を含む。**現実のサービス（事業参加契約）**の性格が強い。ただし現状アプリ内で販売していないため、当面この論点は発生しない |

### 現時点での結論

**`kokudaka` と `gacha_ticket` は、デジタルコンテンツに該当する可能性が高い。**
この2つが唯一いま購入可能な商品であるため、**アプリ内課金の要否を検討する必要があるのは
この2つ**ということになる。

`land_plot` の分類は、既存の法務ブロッカー（土地の利用権の確定）が解けるまで
判断できない。この論点は本調査で新たに発生したものではなく、既存の課題と同一。

## ⑦ 課金Webhookの重複受信・署名検証・付与処理の冪等性

**現状ではStripeのWebhookのみが対象。** LINEアプリ内課金のWebhookは未実装のため、
以下はStripeについての確認結果。

### 署名検証

`src/app/api/stripe/webhook/route.ts` で、**処理の最初に**検証している。

```ts
event = stripe.webhooks.constructEvent(rawBody, signature, settings.stripe_webhook_secret);
```

- 生のリクエストボディ（`request.text()`）で検証しており、パース後のオブジェクトではない
- `stripe-signature` ヘッダが無い場合は400
- 検証失敗も400
- Stripeが未設定の場合は503

**署名検証を通過しないリクエストは、DBに一切触れません。**

### 重複受信の防止

Postgres関数 `claim_stripe_webhook_event()` が、**単一トランザクション内で**
「行が無ければ作成 → `SELECT ... FOR UPDATE` → 状態遷移判定 → claim」を行う。

戻り値の `claim_outcome` によって分岐する。

| 結果 | 意味 | 動作 |
|---|---|---|
| `new` / `retryable` | 未処理または再試行可能 | 処理へ進む |
| `duplicate` | 処理済みイベントの再送 | **何もせず200を返す** |
| `in_progress` | 別のリクエストが処理中 | 待たずに終了（併走させない） |
| `dead` | 再試行上限に達した | 200を返してStripeの再送を止め、管理画面での手動再実行に委ねる |

同一 `stripe_event_id` が並行して到達しても、`FOR UPDATE` により二重にprocessingへ
進むことはなく、unique制約違反が呼び出し元へ伝播することもない。

### 付与処理の冪等性

二重の防御になっている。

1. **`purchases` の状態遷移をロックとして使う** — `pending → processing` への
   原子的な更新（guard-clause update）に成功した呼び出しだけが権利付与へ進む。
   既に `processing` / `completed` / `failed` / `refunded` の場合はそこで終了する
2. **`purchase_grant_steps` によるステップ単位の冪等化** — 付与処理は
   `runPurchaseGrant()` に切り出され、ステップごとに claim_token による
   原子的なclaimを行う。途中失敗しても、成功済みステップは再実行されない

決済確定（`purchases.status`）と権利付与（`grant_status`）を分離管理しているため、
「決済は成功したが付与されていない」状態を検出でき、管理画面から再実行できる。

### 自動テストによる裏付け

`tests/integration/stripe-inbox-concurrency.test.ts` が実DBに対して検証している。

| テスト | 内容 |
|---|---|
| 同一 `stripe_event_id` への10並列claim | `new` が1件だけになる |
| `succeeded` 後の再送 | `duplicate` を返す |
| `failed` 後の再claim | `retryable` になり、attempt上限で `dead` になる |
| lease切れ後 | 別workerが再claimでき、古い `claim_token` では完了・失敗のどちらも更新できない |

このほか `purchase-grant-step-concurrency.test.ts` と
`purchase-balance-grant-concurrency.test.ts` が付与処理の冪等性を検証している。
これらはCIの `integration-test` ジョブで毎回実行される。

### 結論

**Stripeについては、署名検証・重複受信・付与の冪等性いずれも実装済みで、
実DBに対する自動テストで裏付けられている。**

ただし以下は未対応。

- **LINEアプリ内課金のWebhookは未実装。** 採用する場合、上記と同等の
  署名検証・inbox・冪等化を新規に作る必要がある。既存のStripe用の仕組み
  （`stripe_webhook_events` テーブルと `claim_stripe_webhook_event()`）と同じ
  設計を流用できる
- **本番のStripe設定が未完了**（`payment_settings` 未設定）のため、
  本番環境での実地確認はまだ行えていない
